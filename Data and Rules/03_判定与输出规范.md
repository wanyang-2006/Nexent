# 03 判定与输出规范 v1.0.0

- 适用范围：`core/api.py` 六个函数的输入输出、角色与状态判定、工单、重判、评测口径
- 机器可读版本：`schemas/*.schema.json`（JSON Schema 2020-12）；样例在 `examples/fixtures/`，第 1 天直接复制到 `core/fixtures/`
- 乙的 `mcp_server/server.py` 只依赖本文与 schemas；字段要改，须甲乙双方同意并记入 `CHANGELOG.md`

---

## 1. 通用约定

| 项 | 约定 |
|---|---|
| 返回类型 | **一律返回 JSON 对象（dict）**，不返回裸列表；可直接 `json.dumps(obj, ensure_ascii=False)` |
| 字段兼容 | 1.x 内只允许新增字段；乙的代码必须忽略不认识的字段 |
| 错误 | 不抛异常，返回 `{"error": "中文说明", "code": "错误码"}`，可带 `detail`。错误码：`ACCOUNT_NOT_FOUND`、`BAD_RULE_VERSION`、`BAD_TIME_FORMAT`、`BAD_PARAM`、`INTERNAL`。乙的 `_call` 捕获异常时也按此格式返回 `code: INTERNAL` |
| 规则版本 | 每个函数都带 `rule_version`（或 `old`/`new`），不做全局切换 |
| 可复现 | 同一数据、同一规则版本、同一参数，输出必须逐字节相同：列表按文中规定排序，工单不含时间戳 |
| 金额 | 数值；v1 为整数元 |
| 时间 | `YYYY-MM-DD HH:MM` |

## 2. 函数契约

| 函数 | 参数 | 返回（schema） |
|---|---|---|
| `get_account(acct_id)` | | `get_account.schema.json` |
| `get_transactions(acct_id, start=None, end=None, limit=50)` | `start`/`end` 闭区间；`limit` 1~200 | `get_transactions.schema.json` |
| `trace_chain(acct_id, max_hops=4, rule_version="v1")` | `max_hops` 1~10 | `trace_chain.schema.json` |
| `check_rules(acct_id, rule_version="v1")` | | `check_rules.schema.json` |
| `make_ticket(acct_id, rule_version="v1")` | 同时写 `tickets/<版本>/<账户>.json` | `make_ticket.schema.json` |
| `rejudge(old="v1", new="v2")` | | `rejudge.schema.json` |
| `get_ticket(acct_id, rule_version="v1")`（乙实现） | 读文件，不存在则调 `make_ticket` | 同 `make_ticket` |

### 2.1 `get_account`

`{acct_id, name, acct_type, open_date, in_count, in_amount, out_count, out_amount, counterparty_count, first_tx_time, last_tx_time}`

- 统计全部交易类型；提现计入 `out_count`/`out_amount`。
- `counterparty_count`：去重对手账户数，不含 `CASH`。
- 无交易时 `first_tx_time`、`last_tx_time` 为 `null`。

### 2.2 `get_transactions`

`{acct_id, start, end, total, count, truncated, transactions: [{tx_id, time, from_acct, to_acct, amount, tx_type, direction}]}`

- 按 `(time, tx_id)` 升序，返回前 `limit` 条。`total` 为范围内总数，`truncated = total > count`。
- `direction`：`转入` / `转出`（相对查询账户）。
- 键名用 `transactions`，与乙 wrapper 把列表包成 `{"transactions": ..., "count": ...}` 的写法一致。

### 2.3 `trace_chain`

`{acct_id, rule_version, window_min, max_hops, chains: [...]}`，链的字段见 02 规范 5.3 节。`chains` 按 `total_amount` 降序、`chain_id` 升序排列；不在任何链上时为空列表。

### 2.4 `check_rules`

`{acct_id, rule_version, hits: [...], counter: [...]}`

- 每项：`{rule_id, rule_name, type, level, evidence_tx_ids, detail}`，可选 `metrics`。
- `hits` 为风险规则命中，`counter` 为反向规则命中；各自按 `rule_id` 升序。
- 未命中的规则不列出。

## 3. 角色判定

在账户所在的**主链**上判断。主链：`total_amount` 最大的链，相同时取 `chain_id` 较小者。记账户 v 在主链上的转入边数 `indeg`、转出边数 `outdeg`、转出收款方去重数 `recv`。按顺序判定，命中即停：

| 顺序 | 条件 | 角色 |
|---|---|---|
| 0 | 不在任何链上 | 无 |
| 1 | `indeg = 0` | 疑似受骗付款端 |
| 2 | `outdeg = 0` | 末端 |
| 3 | `recv ≥` 该版本 R03 的 `min_receivers` | 拆分端 |
| 4 | 所有转入边的付款方都是“疑似受骗付款端” | 一级收款端 |
| 5 | 其他 | 中转端 |

答案表 `eval/answer.csv` 中的 role 按同一规则登记。分层中转的 L1 为一级收款端，L2、L3 为中转端。

## 4. 状态判定

记 H 为命中的风险规则集合（含 R07、R11），K 为命中的反向规则集合，`on_chain` 为账户是否在任一链上。按顺序判定，命中即停：

| 顺序 | 条件 | 状态 | 代码 |
|---|---|---|---|
| 1 | H 为空 且 不在链上 | 未见异常 | CLEAR |
| 2 | `|H| ≥ 2` 且 在链上 且 角色 ∈ {一级收款端, 中转端, 拆分端} | 建议人工复核 | REVIEW |
| 3 | H 非空 且 K 非空 | 证据不足 | INSUFFICIENT |
| 4 | 其他（H 非空，或在链上） | 存在风险信号 | RISK_SIGNAL |

- 顺序 2 在 3 之前：有工资入账的中转账户仍判“建议人工复核”，反向证据照常写进工单，不降级。
- 严重度（重判时判断升级/降级）：CLEAR 0 < RISK_SIGNAL 1 < INSUFFICIENT 2 < REVIEW 3。

典型结果（设计预期，以实测为准）：

| 账户 | v1 | v2 |
|---|---|---|
| 快进快出、分层、拆分的一级收款端/中转端/拆分端 | 建议人工复核 | 建议人工复核 |
| 受骗付款端、末端 | 存在风险信号 | 存在风险信号 |
| C05/C06 一级收款端 | 存在风险信号（R04、R08 命中但不在链上） | 建议人工复核 |
| C05/C06 受骗付款端 | 未见异常 | 存在风险信号 |
| 高频商户 | 证据不足（R02 + R10） | 证据不足 |
| 工资企业、普通员工 | 未见异常 | 未见异常 |
| D3 的 P | 未见异常 | 证据不足（R01 + R09，在链上为一级收款端） |
| D3 的 F、L | 未见异常 | 存在风险信号（v2 中 F→P→L 成链，分别为疑似受骗付款端、末端） |

D3 的 F、L 在 v2 变为“存在风险信号”不计入误报（误报只统计“建议人工复核”），但会出现在 `rejudge` 的变化列表中，演示时应如实说明。

## 5. 工单

结构见 `schemas/make_ticket.schema.json`，样例 `examples/fixtures/make_ticket.json`。

| 字段 | 规定 |
|---|---|
| `ticket_id` | `TK-<版本>-<账户>` |
| `spec_version` | 本规范版本 |
| `acct_id`、`rule_version` | |
| `status`、`status_code` | 第 4 节 |
| `role` | 第 3 节 |
| `chain_id` | 主链编号；不在链上为 `null` |
| `conclusion` | 一句话，≤ 200 字。在链上时必须包含 `chain_id`；**不得出现禁用词**（`enums.yaml` 的 `conclusion_banned_words`，只检查本字段） |
| `supporting_evidence` | `[{tx_id, desc}]`：风险规则证据与该账户在主链上的边，去重，按时间升序，最多 10 条。状态不是“未见异常”时至少 1 条。`tx_id` 必须真实存在 |
| `counter_evidence` | `[{rule_id, rule_name, desc, tx_ids}]`：反向规则命中 |
| `missing_evidence` | `[{code, desc}]`，**不得为空**，按下表顺序生成 |
| `rule_basis` | `[{rule_id, rule_name, aligned_to}]`：全部命中规则（风险 + 反向），按 `rule_id` 升序 |
| `suggested_actions` | 由状态唯一决定：REVIEW→`[建议人工复核]`，RISK_SIGNAL→`[建议关注后续交易]`，INSUFFICIENT→`[建议补充材料]`，CLEAR→`[]` |

`missing_evidence` 生成规则：

| 代码 | 条件 | desc |
|---|---|---|
| `GAP_KYC` | 总是 | 对手方账户的开户与实名信息 |
| `GAP_MEMO_DEVICE` | `supporting_evidence` 非空 | 转账附言与登录设备信息 |
| `GAP_CALLBACK` | 在链上 | 付款方的回访或报案记录 |
| `GAP_EXT` | 主链上任一账户有提现到 CASH | 资金提现后的去向（链路止于现金出口 CASH） |
| `GAP_HISTORY` | 命中 R08 或 R11 | 数据时间范围之外的历史交易 |
| `GAP_BIZ` | K 非空 | 反向证据的业务背景核实（工资发放单位、商户经营资质） |

`conclusion` 推荐模板（可改措辞，但不得用禁用词，不得给出定性结论）：

- REVIEW：`该账户在资金链 {chain_id} 中表现为{role}，命中 {n} 条风险规则（{规则号}），建议人工复核。`
- INSUFFICIENT：`该账户命中风险规则（{规则号}），同时存在反向证据（{规则号}），现有证据不足以判断，建议补充材料。`
- RISK_SIGNAL：`该账户[在资金链 {chain_id} 中表现为{role}，][命中 {规则号}，]存在风险信号，建议关注后续交易。`
- CLEAR：`在本数据范围内未发现风险规则命中，也不在已识别的资金链上。`

落盘：`json.dumps(ticket, ensure_ascii=False, indent=2)`，UTF-8，字段顺序同 schema。

## 6. 重判

`rejudge(old, new)` 对 accounts.csv 中**全部账户**分别按两个版本判定，只列状态变化的账户。

```text
{old, new,
 changed: [{acct_id, old_status, new_status, direction, old_role, new_role,
            old_chain_id, new_chain_id, rule_changes: {added, removed}, reason}],
 summary: {total, changed, upgraded, downgraded, by_transition}}
```

- `changed` 按 `acct_id` 升序。`direction` 由严重度比较得出：`升级` / `降级`。
- `rule_changes.added` / `removed`：新版本相对旧版本多命中 / 少命中的规则号（风险和反向都算），升序。
- `reason` 由以下片段按顺序用“；”连接：
  1. 每条新增命中：`新命中 R01（快进快出，window_min 60→120）`；该规则参数无变化时省略括号中的参数部分，新规则写 `新命中 R11（多个首次对手集中转入，v2 新增规则）`
  2. 每条不再命中：`不再命中 R0x（名称）`
  3. 链变化：`进入资金链 L-…（角色）` / `离开资金链 L-…` / `所在资金链由 L-… 变为 L-…`
- `by_transition` 键为 `旧状态→新状态`，值为个数。
- 300 个账户全量重判应在数秒内完成（启动时建好按账户的索引）。

## 7. 评测口径（`core/evaluate.py`）

| 指标 | 定义 |
|---|---|
| 埋入链路数 | answer.csv 中不同 `chain_id` 数（v1 为 12） |
| 识别链路数 | 对每条答案链，取其账户集合 G；若某条系统链的 `accounts` 覆盖 G 中 ≥ 60% 的账户，算识别 |
| 漏检链路数 | 埋入数 − 识别数 |
| 链边召回 / 精确（可选） | 用 `answer_tx.csv`：系统链边与答案链边的交集 / 答案链边数；交集 / 系统链边数 |
| 账户召回 | 答案角色为一级收款端、中转端、拆分端的账户中，状态为“建议人工复核”的比例 |
| 误报账户数 | 答案中 `role=无` 的账户中，状态为“建议人工复核”的个数。分母：1 家工资企业 + 28 名纯员工 + 30 家商户（做 D3 时再加 F、P、L 和第二家企业），共 59 或 63 |
| 证据不足数 | `role=无` 且状态为“证据不足”的个数，单列 |
| 背景账户告警数 | 不在 answer.csv 中的账户，状态不是“未见异常”的个数，单列（主要来自 R02 背景噪声） |
| 状态变化 | `rejudge(v1, v2)` 的 `summary` |

结果写入 `eval/result.md`，注明 `dataset_id` 与规则版本。对外表述一律写“在本作品设定的仿真场景内”；v2 演示链是专门设计的，不代表泛化效果。
