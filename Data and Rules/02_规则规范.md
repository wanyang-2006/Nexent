# 02 规则规范 v1.0.0

- 适用范围：`rules/rules_vN.yaml` 的格式、每条规则的精确定义、资金链追踪的定义、规则版本差异格式
- 机器可读版本：`rules/rules_v1.yaml`、`rules/rules_v2.yaml`；规则实现与必需参数的注册表在 `enums.yaml` 的 `rule_impls`
- 所有阈值都是**仿真内部规则**，不是任何官方要求。对外文档统一这样写

---

## 1. 规则文件结构

```yaml
spec_version: 1.0.0          # 本规范版本
version: v2                  # 规则集版本，^v\d+$
based_on: v1                 # 上一版本；v1 为 null
source: 仿真内部规则（非官方要求）
evidence_limit: 10           # 每条命中最多返回的证据交易号
trace: {...}                 # 追链参数，见第 5 节
rules:
  - rule_id: R01             # ^R\d{2,}$，全局唯一，永不复用
    name: 快进快出           # 同一 rule_id 在各版本中 name、type 不变
    type: risk               # risk 风险规则 / counter 反向规则
    level: 高                # 高 / 中 / 低
    impl: fast_in_out        # 实现函数，必须在 enums.yaml 的 rule_impls 中登记
    in_types: [转账]         # 统计的转入交易类型（impl 需要时必填）
    out_types: [转账]        # 统计的转出交易类型（impl 需要时必填）
    params: {...}            # impl 要求的参数必须齐全，不得多出未登记的参数
    aligned_to: "仿真内部规则v2#R01"   # 以后可改为法规条目，如 "反电信网络诈骗法#第X条"
    desc: 一句话中文说明     # 用于渲染知识库 kb/rules_vN.md，必须与参数数字一致
    state: active            # 可选：active（默认）/ deprecated
```

代码约定：

- `core/rules.py` 用 `IMPLS = {"fast_in_out": check_fast_in_out, ...}` 按 `impl` 分发。YAML 中出现未登记的 `impl` 直接报错，防止漏实现。
- 一个 `impl` 可以被多条规则复用（换参数即可新增规则，不必写新函数）。
- 读取路径：`ROOT / "Data and Rules" / "rules" / f"rules_{version}.yaml"`。版本不存在返回错误码 `BAD_RULE_VERSION`。
- 启动时把所有版本加载并缓存，规则文件改动后需重启服务。

## 2. 统计口径与窗口约定

### 2.1 交易类型

| 规则 | 转入统计 | 转出统计 |
|---|---|---|
| R01、R04、R06 | 转账 | 转账 |
| R02 | 转账、消费 | — |
| R03 | — | 转账 |
| R05、R08、R11 | 转账 | — |
| R09 | 工资 | — |
| R10 | 消费 | — |

- 工资不计入任何风险规则，只用于 R09。消费只进入 R02、R10。提现不进入任何规则和追链，只作为工单缺口 `GAP_EXT` 的依据。
- 口径写在每条规则的 `in_types`/`out_types` 中，改口径就是改 YAML，属于规则版本变化。

### 2.2 时间窗

记锚点交易时间为 t，窗口长度为 W 分钟：

| 窗口 | 区间 | 用于 |
|---|---|---|
| 聚合窗口 | `[t, t+W]` | 统计锚点及其后的同向交易（R01 的转入、R02、R03、R11） |
| 前向窗口 | `(t, t+W]` | 锚点之后的反向交易（R01 的转出、追链向下） |
| 向上窗口 | `[t−W, t)` | 追链向上 |
| 自然日 | `00:00`~`23:59` | R04、R05 |

上界一律包含。时间差按分钟整数计算。同一分钟内的先后以 `tx_id` 为准。

### 2.3 通用定义

- **首次对手**：账户 a 在时间 t 收到对手 b 的交易，若数据中在此之前（时间更早，或同一分钟且 `tx_id` 更小）a 与 b 之间没有任何类型、任何方向的交易，则 b 是 a 在 t 时的首次对手。只在数据时间范围内判断，工单需附缺口 `GAP_HISTORY`。
- **数据起始日**：`dataset_meta.time_range[0]` 的日期（v1 为 2026-03-01）。
- **来源 / 收款方**：按账户号去重；`CASH` 不算来源或收款方。
- **证据**：每条命中返回 `evidence_tx_ids`，按时间升序，去重，最多 `evidence_limit` 条；多个窗口都命中时取第 3 节各规则写明的“代表窗口”。

## 3. 规则 v1（10 条）

| 编号 | 名称 | 类型 | impl | 精确定义 | 代表窗口与证据 |
|---|---|---|---|---|---|
| R01 | 快进快出 | 风险 | fast_in_out | 对每笔转入 i（时间 t）：`IN` = `[t, t+W]` 内转入合计，`OUT` = `(t, t+W]` 内转出合计；`IN ≥ min_amount` 且 `ratio_min ≤ OUT/IN ≤ ratio_max` 即命中。W=`window_min`=60，ratio 0.9~1.1，min_amount 10000 | `IN` 最大的命中窗口；证据为窗口内全部转入与转出 |
| R02 | 短时多来源集中转入 | 风险 | multi_source_in | 对每笔转入（时间 t）：`[t, t+W]` 内转入来源去重数 ≥ `min_sources` 即命中。W=60，min_sources 3 | 来源数最多的窗口；证据为窗口内转入 |
| R03 | 拆分转出 | 风险 | split_out | 只看单笔 ≤ `max_single` 的转出。对每笔这样的转出（时间 t）：`[t, t+W]` 内此类转出的收款方去重数 ≥ `min_receivers` 且合计 ≥ `min_total` 即命中。W=60，4 个，9999，20000 | 收款方最多的窗口；证据为窗口内转出 |
| R04 | 余额清零 | 风险 | day_clearout | 对每个自然日：当日转入 `IN ≥ min_amount` 且 `ratio_min ≤ OUT/IN ≤ ratio_max`。0.95~1.1，10000 | `IN` 最大的一天；证据为当日转入与转出 |
| R05 | 新开账户大额转入 | 风险 | new_account_inflow | `0 ≤ (数据起始日 − open_date) < max_age_days`，且某自然日转入合计 > `day_in_amount`。30 天，20000 | 转入最多的一天；证据为当日转入 |
| R06 | 夜间大额 | 风险 | night_large | 存在转入或转出，时间的小时数在 `[hour_from, hour_to)` 内且金额 > `amount`。0~5 点（即 00:00~04:59），10000 | 全部符合的交易 |
| R07 | 多层链路 | 风险 | long_chain | 账户在同一规则版本识别出的某条资金链上，且该链 `hops ≥ min_hops`。3 跳 | `hops` 最大的链；证据为该链交易号 |
| R08 | 首次对手大额转入 | 风险 | first_cp_large | 存在转入金额 > `amount`，且对手为首次对手（2.3 节）。20000 | 全部符合的转入 |
| R09 | 稳定工资收入 | 反向 | salary_income | 工资转入笔数 ≥ `min_count`。1 笔（7 天数据偏弱；90 天数据应改为 3） | 全部工资转入 |
| R10 | 商户经营特征 | 反向 | merchant_profile | `acct_type=商户`，消费转入付款方去重数 ≥ `min_payers`，金额中位数 ≤ `median_max`。10 个，500 元 | 最早的 10 笔消费转入 |

`detail` 是给人看的一句话，必须包含关键数字，例如：`10:05 起 60 分钟内转入 62000 元，转出 60500 元（97.6%）`。可选字段 `metrics` 放机器可读的数字，如 `{"in": 62000, "out": 60500, "ratio": 0.976}`。

## 5. 资金链追踪定义（`core/trace.py`）

### 5.1 参数（规则文件的 `trace` 段）

| 键 | v1 | 说明 |
|---|---|---|
| `window_from` | `R01.window_min` | 追链时间窗 W 取自 R01，所以 v2 修改 R01 会同时改变追链结果 |
| `edge_types` | `[转账]` | 可成为链边的交易类型 |
| `seed_min_amount` | 3000 | 链边最小金额 |
| `min_chain_amount` | 10000 | 链内至少有一笔不低于此金额 |
| `conserve_ratio` | 0.5 | 节点守恒比例 |
| `max_component_edges` | 500 | 安全上限，超过即截断并在结果中标 `truncated` |

### 5.2 定义：链接图

1. **候选边**：`tx_type ∈ edge_types`，双方都是账户（不含 `CASH`、`EXT-`），`amount ≥ seed_min_amount` 的交易。
2. **链接** `e1 → e2`：同时满足
   - `e1.to_acct == e2.from_acct`（记为节点 v）；
   - `e1.time < e2.time ≤ e1.time + W`；
   - 向下守恒：v 在 `(e1.time, e1.time+W]` 内的候选边转出合计 ≥ `conserve_ratio × e1.amount`；
   - 向上守恒：v 在 `[e2.time−W, e2.time)` 内的候选边转入合计 ≥ `conserve_ratio × e2.amount`。
3. **资金链**：把候选边当作点、链接当作有向边，取弱连通分量。只保留**至少含 1 个链接**、且最大单笔 ≥ `min_chain_amount` 的分量。没有任何链接的候选边不属于任何链。
4. **全局计算**：每个规则版本在启动时（或第一次调用时）对全部数据算一次并缓存。`trace_chain(acct)` 返回包含该账户的所有链，R07 也使用这份结果。因此同一条链从任何账户查询，得到的链和编号都相同。

为什么这样定义（相对甲文档旧版 4.1 的修正）：

| 旧做法的问题 | 现定义 |
|---|---|
| 无条件接受目标账户的“种子边”，C05 在 v1 也会被判为在链上（种子边自己就满足“边数 ≥2”），v1→v2 的变化消失；D3 也会被误判成链 | 一条边只有和另一条边形成时间窗内的链接才算链 |
| 拆分转出时分支金额小，路径守恒会过滤掉 | 守恒只在节点上检查 |
| 查受骗账户时只向下、查末端时只向上，会漏掉兄弟分支 | 弱连通分量天然包含上游、下游和兄弟分支 |

链接图按时间严格递增，必然无环，最长路径可以直接 DFS。

### 5.3 输出字段

| 字段 | 定义 |
|---|---|
| `chain_id` | `"L-" + 链内最小 tx_id` |
| `hops` | 链接图中最长路径的边数（交易笔数）。分层中转“受骗方→L1→L2→L3→末端”为 4 |
| `total_amount` | 源边（没有前驱链接的边）金额合计 |
| `duration_minutes` | 链内最晚交易与最早交易的时间差 |
| `accounts` | 链内全部账户，按（距源点的深度，acct_id）排序 |
| `tx_ids` | 链内全部交易号，升序 |
| `edges` | `[{tx_id, from_acct, to_acct, time, amount}]`，按时间升序 |
| `roles` | `{acct_id: role}`，按 03 规范第 3 节判定 |
| `truncated` | 是否因 `max_hops` 或 `max_component_edges` 截断了返回的边 |

`max_hops`（`trace_chain` 的参数，默认 4，取值 1~10）只限制**返回**多少：在链的账户图（无向）中，从查询账户出发 BFS，只返回两端距离都 ≤ `max_hops` 的边。`chain_id`、`hops`、`total_amount`、`duration_minutes`、`roles` 始终描述整条链。

### 5.4 降级方案

时间不够时可只实现“链接 + 连通分量”，不做 `max_hops` 截断（v1 数据中单条链最多 10 条边：拆分转出 2 笔受骗转入 + 8 笔拆分，全部返回也不会过长）。

## 6. 版本管理与差异格式

### 6.1 规则版本

- 旧版本文件发布后不再修改（只允许修正错别字和 `desc` 中与参数不一致的描述）。改阈值就新建版本。
- 新版本必须写 `based_on`。
- `rule_id` 不复用；同一 `rule_id` 的 `name`、`type`、`impl` 在各版本中不变。想改含义就新开编号，旧规则在新版本中删除或标 `state: deprecated`。
- 知识库文件 `kb/rules_vN.md` 由脚本从 YAML 渲染，不手写，保证知识库与引擎一致。

### 6.2 差异文件 `kb/rules_diff_<旧>_<新>.md`

由脚本生成，结构固定（JSON 形式也可，同样字段）：

```json
{
  "from": "v1", "to": "v2",
  "added":   [{"rule_id": "R11", "name": "多个首次对手集中转入"}],
  "removed": [],
  "changed": [{"rule_id": "R01", "field": "params.window_min", "old": 60, "new": 120}],
  "trace_changed": [{"field": "W", "old": 60, "new": 120, "reason": "window_from=R01.window_min"}]
}
```

Markdown 渲染为三张表：新增规则、删除规则、参数变化。`rejudge` 的 `reason` 中引用的参数变化与本文件一致。

## 7. 新增规则的流程

1. 在 `enums.yaml` 的 `rule_impls` 中登记（复用已有 impl 可跳过）。
2. 新建 `rules_v(N+1).yaml`，写 `based_on`，加入规则，分配新的 `rule_id`。
3. `core/rules.py` 实现函数并加入 `IMPLS`。
4. 运行 `validate_spec.py`，再跑 `selfcheck`，对比命中变化。
5. 渲染 `kb/rules_v(N+1).md` 与差异文件，交乙更新知识库。
6. 在 `CHANGELOG.md` 记录。
